## Long-term architecture

You will maintain this code for years. Judge each change by whether it leaves code easier to change, test and navigate. A working fix that spreads knowledge across more callers is unfinished.

Vocabulary (from Matt Pocock's codebase-design skill):
- Module: anything with an interface and implementation, function to package.
- Interface: all a caller must know to use it correctly: types, invariants, ordering, error modes, config.
- Deep module: much behaviour behind a small interface. Shallow: interface nearly as complex as implementation.
- Seam: where an interface lives; behaviour changes there without editing callers.
- Leverage: what callers gain from depth. Locality: what maintainers gain as change, bugs and tests concentrate in one place.

Principles:
- Deletion test: if deleting a module makes its complexity reappear across callers, it earns its place; if complexity vanishes, it was a pass-through.
- The interface is the test surface. Test through it, not past it. Once tests cover a deepened interface, delete tests of the shallow modules it absorbed.
- One adapter is a hypothetical seam; two make it real. Don't add a seam nothing varies across.
- Accept dependencies, don't create them. Return results, don't produce side effects.

Use terms from `GLOSSARY.md` or `CONTEXT.md` if present. Read relevant `docs/adr/` decisions and don't re-litigate them; raise a conflict only for real friction, naming the ADR. Record a new ADR only for a decision that is hard to reverse, surprising without context and a real trade-off.

## Code

Read the task and trace the code it touches end to end, then stop at the first rung that holds:
1. Not needed.
2. Already in this codebase: reuse the helper, util or pattern.
3. Standard library.
4. Native platform feature.
5. Installed dependency.
6. Smallest clear implementation that meets the requirements.
The smallest change in the wrong place is a second bug.

- Check every caller of what you touch. Fix a shared function once, not just the caller the ticket names, or its siblings stay broken.
- No speculative abstractions, dependencies or boilerplate. Deletion over addition, boring over clever, fewest files.
- Between equal-sized options, pick the edge-case-correct one. Minimal means less code, not a flimsier algorithm.
- Mark deliberate corner-cuts with a known ceiling (global lock, O(n²) scan, naive heuristic) with a `CEILING:` comment naming the limit and upgrade path, so the next reader finds it before it bites.
- Remove code your change makes obsolete.
- Never minimal on input validation at trust boundaries, error handling that prevents data loss, security or accessibility.
- Non-trivial logic ships with one runnable check that fails if it breaks: the project's test setup, else a small assert script, never a new framework. Trivial one-liners need none.
- Test bar: a test must be able to fail for a plausible real bug in behaviour a user or caller observes. Fails the bar: tautologies (mock returning what it was told, restated constant, static-markup snapshot), implementation details (call counts, call order, private state), near-duplicates at the same seam, pass-through glue, third-party behaviour.

## UI state lives in reducers

Keep UI logic out of components, in a pure reducer `(state, action) => state`. Actions name everything that can happen: user input, requests starting, succeeding and failing, timers firing. Components render state and dispatch actions; they don't decide what happens next.
- State is a discriminated union (`idle`, `loading`, `error`, `success`), not booleans that allow impossible combinations.
- Handle every action in every state, even by ignoring it. A late response, double click or retry after error must not leave the UI stuck.
- Effects (fetching, timers, storage) stay outside the reducer; the component or a hook runs them and dispatches results.
- Test the reducer directly with the project's runner, outside the browser: action sequences in, state asserted, including failure and out-of-order paths.
- React: `useReducer` for state one component owns. Shared state: Zustand with reducer state under one key: `create((set) => ({ state: initial, dispatch: (action) => set((store) => ({ state: reducer(store.state, action) })) }))`. Not Zustand's `redux` middleware: it shallow-merges, so stale fields survive transitions. Add Zustand only when shared state needs it.
- Keep an existing state library (Redux, XState, Jotai); don't add or migrate to Zustand. Outside React, use the framework's store.
Apply when a component juggles related state, async flows or error handling. A single toggle or input stays plain local state.

## Writing

For reports, code comments and docs you edit:
- Plain words, short sentences, active voice, named actors.
- Exact: "throws on an empty list", not "has edge-case issues". Exact figures; label estimates.
- Separate fact from opinion; "I think" for views. Never invent facts, figures or quotes.
- Commit to a point; don't hedge. Understate rather than overstate, or maintainers learn to discount you.
- No summary restating what was just said.
- No em dashes. Sentence case for headings and labels. Avoid: delve, elevate, seamless, robust, leverage, unlock, empower, streamline, harness.
