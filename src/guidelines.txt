## Long-term architecture

Treat this codebase as one you will maintain for years. Judge every change by whether it leaves the code easier to change, test and navigate. A fix that works but spreads knowledge across more callers is unfinished.

Use this vocabulary, adapted from Matt Pocock's codebase-design skill:

- Module: anything with an interface and an implementation, from a function to a package.
- Interface: everything a caller must know to use a module correctly: types, invariants, ordering, error modes and configuration.
- Deep module: a lot of behaviour behind a small interface. Shallow module: the interface is nearly as complex as the implementation.
- Seam: the place a module's interface lives, where behaviour can change without editing callers.
- Leverage: what callers gain from depth. Locality: what maintainers gain, because change, bugs and tests concentrate in one place.

Principles:

- Deletion test: imagine deleting a module. If its complexity would reappear across callers, it earns its place. If it would simply vanish, it was a pass-through.
- The interface is the test surface. Test behaviour through it, not past it. Once tests cover a deepened interface, delete the tests of the shallow modules it absorbed.
- One adapter is a hypothetical seam; two make it real. Do not add a seam that nothing varies across.
- Accept dependencies rather than creating them. Return results rather than producing side effects.

If the repository has `GLOSSARY.md` or `CONTEXT.md`, use its terms in code, tickets and reports. Read relevant decisions in `docs/adr/` and do not re-litigate them; raise a conflict only when the friction is real, naming the ADR. Record a new ADR only for a decision that is hard to reverse, surprising without context and the result of a real trade-off.

## Code

Before writing code, stop at the first rung that holds:

1. Not needed at all.
2. Already in this codebase. Reuse the existing helper, util or pattern.
3. The standard library does it.
4. A native platform feature covers it.
5. An installed dependency solves it.
6. Write the smallest clear implementation that meets the requirements.

Climb the ladder after reading the task and tracing the code it touches end to end. The smallest change in the wrong place is a second bug.

- Check every caller of anything you touch. Fix a shared function once rather than patching the caller the ticket names, or its siblings stay broken.
- No speculative abstractions, dependencies or boilerplate. Deletion over addition, boring over clever, fewest files.
- Between equal-sized options, pick the one that is correct on edge cases. Minimal means less code, not a flimsier algorithm.
- Mark a deliberate corner-cut with a known ceiling (global lock, O(n²) scan, naive heuristic) with a `CEILING:` comment naming the limit and the upgrade path, so the next reader finds it before it bites.
- Remove code your change makes obsolete.
- Never minimal on input validation at trust boundaries, error handling that prevents data loss, security or accessibility.
- Non-trivial logic ships with one runnable check that fails if the logic breaks. Use the project's test setup; without one, a small assert-based script, not a new framework. Trivial one-liners need none.

## UI state lives in reducers

Keep the logic that drives a UI out of its components. Model it as a pure reducer: `(state, action) => state`. Actions name everything that can happen: user input, requests starting, succeeding and failing, timers firing. Components render state and dispatch actions; they do not decide what happens next.

- Make state a discriminated union of the states the UI can be in (`idle`, `loading`, `error`, `success`), not a bag of booleans that allows impossible combinations.
- Handle every action in every state, even if the answer is to ignore it. A late response, a double click or a retry after an error must not leave the UI stuck.
- Keep effects (fetching, timers, storage) outside the reducer. The reducer returns the next state; the component or a hook runs the effect and dispatches the result.
- Test the reducer directly with the project's test runner, outside the browser: feed action sequences and assert on state, including failure and out-of-order paths.
- In React, keep state one component owns in `useReducer`. For state several components share, use Zustand with the reducer state under one key: `create((set) => ({ state: initial, dispatch: (action) => set((store) => ({ state: reducer(store.state, action) })) }))`. Avoid Zustand's `redux` middleware: it shallow-merges the reducer result, so fields from the previous state survive a transition. Add Zustand when shared state needs it, not for local state.
- If the project already uses another state library, such as Redux, XState or Jotai, keep it. Do not add Zustand beside it or migrate to it. Outside React, use the framework's own store.

Apply this when a component juggles several related pieces of state, async flows or error handling. Leave a single toggle or input as plain local state.

## Writing

Applies to reports, code comments and any docs you edit.

- Plain words, short sentences, active voice with named actors.
- Be exact: "throws on an empty list" not "has edge-case issues". Keep figures exact and label estimates.
- Keep fact and opinion visibly separate; say "I think" for a view. Never invent facts, figures or quotes.
- Commit to a point instead of hedging both sides. Understate rather than overstate, or maintainers learn to discount you.
- No summary sentence that restates what was just said.
- No em dashes. Sentence case for headings and labels. Avoid: delve, elevate, seamless, robust, leverage, unlock, empower, streamline, harness.
